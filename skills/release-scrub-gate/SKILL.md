# Release Scrub Gate — 发布脱敏三重门

> **「文档自称已脱敏」不能当证据。** 发布前应按固定流程检查，避免示例、日志或历史记录意外带出敏感信息。

## 0. 为什么要有这道门

| 你以为的 | 实际的 |
|---|---|
| 我写的文件我自己检查过 | **作者盲区**：自己写的东西自己看不见问题 |
| 机械扫描过了就安全 | 只能抓**确定性**模式（密钥/IP），抓不到**语义泄露** |
| 一个 agent 审一遍就够 | 角度单一 + 互相锚定；**两个独立 agent 才有覆盖** |
| 改掉再推就干净了 | **git 历史永远留着**——改文件 ≠ 删历史 |

## 1. 三重门（顺序不可颠倒）

| 层 | 谁做 | 权威范围 | 性质 |
|---|---|---|---|
| **L1 机械** | grep 正则 / 仓库自带敏感词扫描 | 凭据、密钥、token、IP、账号名、主机名 | **确定性**，命中即中止 |
| **L2 语义** | **2 个独立子 agent**（角度错开） | 语义泄露、反推风险、示例措辞、内部结构残留 | **概率**，必须证据式 |
| **L3 责任** | **人** | 最终签收 | agent 不担责，人担责 |

**L1 先于 L2**：机械扫描是确定性的，几秒钟就能排掉一大类；别让 agent 去找密钥（它会漏）。

## 2. 迭代循环（核心机制）

```
第 1 轮：L1 机械扫描 → 2 个 agent 并行审 → 汇总 findings
         ↓ 有发现
        修（由主 agent 修，审核 agent 不许动文件）
         ↓
第 2 轮：换 2 个【全新】agent 复审（不复用上一轮的，它们会锚定自己上次的结论）
         ↓ 仍有发现
        修 → 第 3 轮
         ↓ 连续一轮【零发现】
        ✅ 脱敏结束 → L3 人工签收
```

**收敛判据（必须同时满足才算一轮 clean）**：

1. 两个 agent 的 `findings` 都是**空数组**；
2. 两个 agent 都在 `verdict` 里**明确声明已查哪些类别、每类无命中**；
3. 主 agent 自己也复跑一遍 L1 机械扫描确认 0 命中。

**成本闸门**：一轮通过才算结束；**最多 5 轮**。若连续轮次都栽在**同一类**问题上，说明问题不在内容而在**你的写法**——停下来改写法，别再重复派 agent。

> 第 3 轮之后仍在同一位置反复出错时，**不要硬撑轮次**：那说明缺的是一条机械自检规则，不是缺一轮审核。

## 3. 硬纪律（违反即失效）

1. **审与改分离。** 审核 agent 只报告、不修改；修改后由新的 agent 复审。
2. **证据式 findings。** 每条 finding 仅在本地对话中记录，包含文件、行号、原文引用、严重度、原因和修复建议；任何原文引用不得复制进公开文档、日志或 CI。
3. **两个 agent 互相不可见。** 并行派发、各自独立，不要让第二个看到第一个的结论。
4. **角度必须错开**：一方关注凭据、身份、主机与路径；另一方关注业务内幕、个人隐私、示例措辞及组合反推风险。
5. **复审要看 diff 也要看全文。** 修复本身可能引入新泄露。
6. **每轮换新 agent。** 复用会锚定上次结论，还会把"上次没报"当成"没问题"。
7. **命中报告只显示最小定位信息。** 不得把匹配原文或整行上下文写入 JSON、终端或 CI 日志；`--show-sensitive-context` 仅限本地人类可读输出，不能与 `--json` 同时使用。
8. **扫描路径也要最小化**：终端摘要只显示根目录名称，不输出完整本机路径。

## 4. 扫描器范围说明

| 范围 | 行为 |
|---|---|
| 文件名 | 检查支持文本类型的文件名；相对路径会按匹配规则脱敏，同一脱敏路径的重复命中合并并显示次数 |
| 文件内容 | 检查当前工作树支持的文件内容；同一安全路径、行号、类别的重复规则命中合并并显示次数，不同类别分别报告 |
| 隐藏目录与隐藏文件 | 扫描支持的文本类型；跳过版本控制元数据、依赖/虚拟环境目录和符号链接目标内容（仍检查符号链接名称）。无效扫描根目录以非零码退出。 |
| Git 历史 | 不扫描旧提交对象；发布前须单独检查待发布差异及相关历史 |

**本地词表**：默认查找扫描根目录下的 `scrub-patterns.local.txt`，不存在时按无本地规则运行；显式传入 `--local` 时路径必须存在且为文件。该文件提供额外扫描规则，不会被自身扫描；与通用规则的重叠命中会合并到同一位置报告。

## 5. 泄露模式示例（机械扫描可能漏报）

| 泄露模式 | 为什么机械扫描抓不到 |
|---|---|
| 示例中暗示内容是为某个特定的人准备 | 读者可能结合上下文识别相关对象 |
| 示例行包含私密文件名 | 看起来只是格式示例 |
| 示例里出现真实市场、站点或店铺名 | 容易被当作随手举例 |
| 对现实关系人的性格或评价 | 需要语义判断 |
| 复述事件时复制了原始内容 | 案例本身可能成为新的泄露源 |

这类信息未必是凭据或秘密，但仍可能揭示个人或业务信息，需要语义审核。

**两条配套硬规则**：

1. **审核 agent 的 finding 必须带原文引用**（否则不可复核）——但那份报告只进入本地对话，不得写入公开文件；
2. **公开文档里的案例只写模式、不写具体值**；不能抽象化时就不发布该案例。

## 6. GitHub 的现实（改文件 ≠ 删历史）

发布后发现泄露，推送新版本并不一定会移除旧历史或外部副本。根据敏感度评估公开提交、fork、搜索索引及缓存；历史改写和强制推送不可逆，必须由责任人批准。必要时联系托管平台支持，并验证清理结果。

## 7. 失败模式速查

| 症状 | 原因 | 修法 |
|---|---|---|
| agent 说「干净」但其实有漏 | 浅检、没列已查类别 | 强制要求声明「已查哪些类别、每类无命中」 |
| 两个 agent 结论高度雷同 | 角度没分开 / 互相可见 | 重派，明确分工与隔离 |
| 同一个问题反复出现 | 只修了症状没修生成规则 | 找到产出该内容的模板/工作流一并改 |
| 审核 agent 顺手把文件改了 | 破坏审改分离 | 回滚它的改动，只采纳报告 |
| 跑了 4 轮还没干净 | 内容本身不适合公开 | **升级给人**，考虑这条内容就不该发 |
| 命中或复核后仍发现同类泄露 | 只修了文本，没有检查副本或更新流程 | 全文搜相关文本，并修复生成/发布环节 |



## 8. 接入点（这道门要挂在哪）

**判据：凡是内容离开你控制范围的出口，都要过这道门。**

| 出口 | 挂在哪 | 备注 |
|---|---|---|
| **仓库发布** | 仓库发布脚本（按项目配置，落盘前） | 机械扫描命中即中止，脚本退出码非 0 |
| **知乎 / 小红书 / 公众号 / 微博** | 对应生成技能的 **SKILL.md 里写强制指针** | 生成 ≠ 发布；**发布前**必须过门 |
| **对外交付物**（给客户的文档/资料） | 交付清单里的固定一步 | 客户隐私同样不能带出去 |
| **任何公开仓库的 push** | 提交前 | 尤其是 AGENTS/README 这类容易随手加入示例的文件 |

**机制说明（重要）**：靠"记得去跑"是不成立的。

- 生成类技能里必须写**强制指针**（「本技能产出在发布前必须过 `release-scrub-gate`」），因为只有 SKILL.md 的 name+description 常驻上下文——**指针写在心里等于没写**；
- 脚本类出口（publish 脚本）把扫描做成**硬闸**：命中即 `exit 1`，不给人"这次算了"的机会；
- 平台发布类没有脚本闸门 → 只能靠指针对齐，所以**指针必须显式写着「发布前」**，不能只写「注意脱敏」。

**最容易漏的三个位置**：

1. **示例行**——为了讲清格式而举的例子
2. **案例复盘**——为了说明风险而不小心复制了敏感原文
3. **旧文件与提交历史**——不能因为声称已脱敏就跳过重新检查；删除的旧提交也要纳入暴露面评估
