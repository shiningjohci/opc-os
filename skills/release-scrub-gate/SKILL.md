# Release Scrub Gate — 发布脱敏三重门

> **「文档自称已脱敏」不能当证据。** 一条通用规律：
> 自称「已脱敏」不能当证据——示例行也可能带出真实私密信息。

## 0. 为什么要有这道门

| 你以为的 | 实际的 |
|---|---|
| 我写的文件我自己检查过 | **作者盲区**：自己写的东西自己看不见问题 |
| 机械扫描过了就安全 | 只能抓**确定性**模式（密钥/IP），抓不到**语义泄露** |
| 一个 agent 审一遍就够 | 角度单一 + 互相锚定；**两个独立 agent 才有覆盖** |
| 改掉再推就干净了 | **git 历史永远留着**——改文件 ≠ 删历史 |

## 1. 三重门（顺序不可颠倒）

| 层 | 谁做 | 权威范围 | 性质 |
|---|---|---|---|
| **L1 机械** | grep 正则 / 仓库自带敏感词扫描 | 凭据、密钥、token、IP、账号名、主机名 | **确定性**，命中即中止 |
| **L2 语义** | **2 个独立子 agent**（角度错开） | 语义泄露、反推风险、示例措辞、内部结构残留 | **概率**，必须证据式 |
| **L3 责任** | **人** | 最终签收 | agent 不担责，人担责 |

**L1 先于 L2**：机械扫描是确定性的，几秒钟就能排掉一大类；别让 agent 去找密钥（它会漏）。

### 先判定暴露状态——它决定整个响应（第 0 步，别跳）

同一个发现，「还没推」与「已经在远端」的处置完全不同。**动手前先查远端**：

```bash
git -C <repo> show origin/main:<file> | grep <可疑值>     # 远端当前版本里有没有
gh api repos/<owner>/<repo>/commits/<sha>                 # 旧提交还在不在
gh api repos/<owner>/<repo> --jq '{forks:.forks_count}'   # 有没有被 fork
```

| 状态 | 处置 |
|---|---|
| **还没推**（本地 commit / 未发布） | 修完 → 过三重门 → 再推。下面整套流程适用 |
| **已经在远端** | **这是泄露事件，不是发布检查**：止血 → 查暴露面 → 改历史 → GitHub Support。别用「修完再推」的乐观假设 |

判据：**只要 `git show origin/main:<file>` 命中可疑值，就已经是泄露**——不管它是不是「虚构示例」、是不是「自称已脱敏」。把这次当成发布前检查来跑，会让你只做半套补救。

### L1 的两个已知盲区（会漏报 / 会误报）

- **扫不到 git 元数据**：作者邮箱、commit message、tag 名都不在工作树里，grep 覆盖不到。补一条 `git log --format='%an <%ae>' | sort -u`；要清掉见 `references/history-rewrite.md`。
- **会误报仓库自身地址**：安装文档里的 `owner/repo` 克隆链接不是泄露（它是产物的下载地址）。**不要整文件豁免**（会连带放过该文件里真正的泄露）——让扫描器只跳过「命中文本含完整 `owner/repo` slug」的命中；单独出现的账号名照常报警。

### 跨语料闸：把「别带过去」从纪律变成机器可测试的

`manifest.json` 是**文件级**白名单——它管「哪些文件发布」，管不了「文件里的值」。若泄露值躺在**待发布的文件里**，文件级白名单完全无感。

补法是把边界下推到**内容级**：

```
① 从私有语料抽取专有值 → deny-list（本地）
② 扫发布物：出现任何 deny-list 里的值 → 硬闸拦下
```

**判据**：发布物里出现一个在私有语料里存在过的**值**，就是泄露——不需要理解上下文，**纯机械、可测试**。内容迁移、复制粘贴类失误，从此由机器拦，不靠人记得。

**两个清单都存私有处，绝不随产品发布**：

| 清单 | 内容 | 怎么来 |
|---|---|---|
| `private/deny-list.json`（技能目录内） | 值：人名 / 薪酬形态 / 站点 | 从私有语料自动抽取（可重建） |
| `private/deny-phrases.txt`（技能目录内） | 禁发原句 | 人工维护（不可重建） |

查找顺序：显式参数 → 技能根 `private/`（主副本）→ `scripts/private/` → `~/.config/opc-os/`（兜底副本）。

> **为什么放进技能目录却发不出去**：这两份清单本身就是「哪些值不能见人」的答案——**发布它等于把答案发出去**。所以用**三重保险**卡死：① 不写进发布 manifest 白名单；② 目录名 `private/` 自我声明；③ 发布脚本硬拒 `private/` 与 `deny-*`（机制上：词表不在 manifest 白名单内，塞入即被发布脚本中止）。技能正文只写**指针**，不写内容。

**边界**（别指望它全挡）：抓不到**通用行业词**（如「本土店」单独出现是行业术语），也抓不到**关联性**泄露（真名 + 负面评价、事故指纹）。这类只能靠 L2。分工：

| 层 | 挡什么 |
|---|---|
| 跨语料闸（机械） | 私有语料里的值漏进发布物 |
| 凭据扫描（机械） | key / token / 密码形态 |
| L2 语义审核 | 关联性、组合反推、「通用词 + 具体细节」的组合 |

## 2. 迭代循环（核心机制）

```
第 1 轮：L1 机械扫描 → 2 个 agent 并行审 → 汇总 findings
         ↓ 有发现
        修（由主 agent 修，审核 agent 不许动文件）
         ↓
第 2 轮：换 2 个【全新】agent 复审（不复用上一轮的，它们会锚定自己上次的结论）
         ↓ 仍有发现
        修 → 第 3 轮
         ↓ 连续一轮【零发现】
        ✅ 脱敏结束 → L3 人工签收
```

**收敛判据（必须同时满足才算一轮 clean）**：

1. 两个 agent 的 `findings` 都是**空数组**；
2. 两个 agent 都在 `verdict` 里**明确声明已查哪些类别、每类无命中**；
3. 主 agent 自己也复跑一遍 L1 机械扫描确认 0 命中。

**成本闸门**：一轮通过才算结束；**最多 5 轮**。若连续轮次都栽在**同一类**问题上，说明问题不在内容而在**你的写法**——停下来改写法，别再派 agent（见 §4 的自检三步）。

**反向信号比单条 finding 更强**：两个**互不可见**的 agent **独立命中同一处** = 最高置信度的真问题，优先级高于任何单条 high。别因为它「看起来像示例」「标了虚构」就降级。

> 多轮之后仍在同一位置反复出错时，**不要硬撑轮次**：那说明缺的是一条机械自检规则，不是缺一轮审核。

## 3. 硬纪律（违反即失效）

1. **审与改分离。** 审核 agent **只报告、不修改**。它一改，就失去独立复核（它会把自己改的算作"已清理"）。
2. **证据式 findings。** 每条必须含 `file` / `line` / **`quoted`（原文引用）** / `severity` / `why` / `fix`。**没有原文引用的 finding 不算数；没有引用的「干净」也不算数。**
3. **两个 agent 互相不可见。** 并行派发、各自独立，不要让第二个看到第一个的结论。
4. **角度必须错开**，不是两遍同样的检查：
   - **A：凭据与身份可追溯性** —— 凭据 / 主机网络 / 真人姓名与内部系统 / 私有路径结构
   - **B：业务内幕与个人隐私** —— 业务数字与内幕 / 员工隐私 / 个人财务家庭关系 / 内部决策与上级原话 / **示例措辞** / **组合反推风险**
5. **复审要看 diff 也要看全文。** 修复本身可能引入新泄露（例如把一个敏感值换成另一个同类敏感值）。
6. **每轮换新 agent。** 复用会锚定上次结论，还会把"上次没报"当成"没问题"。

## 4. 这类泄露长什么样（机械扫描全漏）

> **⚠️ 本节及任何公开文档只写「模式」，绝不写具体值。**
> 讲案例时把任何具体值抄进公开文档 = **二次泄露**。
> 修复本身也可能引入二次泄露。

| 泄露模式 | 为什么机械扫描抓不到 |
|---|---|
| 人称暗示「这是为某个特定的人做的」 | **反推线索**：读者能推断出给谁做的 → 熟人可对号入座 |
| 示例行里自然带出真实私密值 | 它是「示例格式」的产物，正则扫不到 |
| 示例里出现真实市场 / 站点 / 店铺名 | 看起来只是随手举的例子 |
| 对真实关系人（上级 / 同事 / 客户）的性格或评价 | **语义级泄露**：复述了真实关系与判断 |
| 复述事件时把原文抄回来 | **写防泄露文档时容易犯**——案例本身变成了新的泄露源 |

**共性：它们都不是「秘密」，但读了就等于知道了私事。** 这类只能靠语义审核发现。

### 什么算泄露（最容易判反的一条）

| 类型 | 判据 | 处置 |
|---|---|---|
| **真实值** | 能推回到某个真实的人 / 店 / 金额 / 日期 | **必须清**，包括进了历史的 |
| **教学占位** | 编出来的、且推不回真实数据（如虚构候选人「张三」、演示用的假金额） | **留着**，标「虚构」。删光数字会让示例失去教学价值，而它们本来就不泄任何东西 |
| **本人署名** | 作者姓名、LICENSE 版权行、个人社交主页链接 | **按用户口径保留**（产品署名不等于泄露），不要顺手清 |
| **第三方个人信息** | 别人的姓名 + 对他的评价 / 薪资 / 经历 | **必须清**，优先级最高（见 §5） |

**判法：拿那个值去搜真实世界能不能定位到人/事。** 「教科书里的虚构月薪」搜不到人，「假如某个示例的数字来自一场真实事件的具体记录」就能定位到具体的人与具体的事——同一个数字，一个是占位、一个是泄露。反过来也不要走极端：把示例里的所有数字都删掉，产出物就没法用了。

**两条配套硬规则**：

1. **审核 agent 的 finding 必须带原文引用**（否则不可复核）——但那份报告**只进本地对话，绝不进任何公开文件**；
2. **公开文档里讲案例只能写模式、不能写值**——做不到抽象化就干脆不写这个案例。

### 案例自检三步（机械执行，别靠记性）

**若同类错误反复出现，说明缺的是一条机械自检规则。**「记住要抽象」没有用，必须机械检查：

1. **抽值**：把案例段落里所有 `「」`、`""`、反引号包着的内容抽出来；
2. **替换测试**：把它们统统换成 `[值]`，如果句子**仍然成立** → 说明这个值不是必需的 → **删掉它**；
3. **回搜**：把删掉的值拿去**全文（及所有副本文件）搜一遍**，确认没有残留在别处。

> 判据：**案例句里出现被引号包起来的专有名词 = 危险信号。** 抽象案例里不需要任何专有名词。

## 5. GitHub 的现实（改文件 ≠ 删历史）

发布后发现泄露，**推一个新 commit 覆盖是不够的**：

- 旧 commit 里的原文**永远可访问**（`github.com/<owner>/<repo>/blob/<旧SHA>/<file>`）
- 搜索引擎可能已索引
- **fork 里的副本无法收回**（先查 `forks_count`！0 fork = 暴露面可控）

**补救顺序**：
1. **先止血**：改内容 + 推新 commit（无论如何都要做）
2. **查暴露面**：`gh api repos/<owner>/<repo> --jq '{forks:.forks_count, stars:.stargazers_count}'`
3. **要不要改历史**：`git filter-repo` / BFG + force push —— **不可逆、会改写所有 SHA**，必须人拍板
4. **事后**：检查搜索引擎缓存；敏感度高时联系 GitHub Support 清理

**判据**：0 fork + 低敏感度 + 受众小 → 可以只做第 1 步并记录决策；有 fork 或高敏感度 → 必须改历史。

**优先级：第三方个人信息 > 自己的业务信息。** 员工 / 候选人 / 客户 / 家人的姓名，以及对他们的评价，是最高等级——当事人无法被找到、无法撤回，且正是 GitHub「敏感数据移除」最对口的情形（无法用换凭据缓解）。**工单正文把这条写在最前面**，比「个人业务信息」的口径更可能获批。

**改历史的完整配方**（备份 → 替换表 → 调用陷阱 → 全历史正反校验 → force push → 残留验证）见 `references/history-rewrite.md`。

### ⚠️ force push **不等于**彻底删除

改历史 + force push 之后，**旧 commit 仍可按 SHA 直接访问**——平台只是把它们变成不可达对象，内容并未从存储中消失。

原因：GitHub 只把旧提交变成「不可达对象」，**不立即物理删除**；知道 SHA 的人（或搜索引擎缓存）依然能读到。

**所以完整流程是三步，不是两步**：

| 步 | 动作 | 效果 |
|---|---|---|
| 1 | 改内容 + 推新 commit | 新版本干净 |
| 2 | `git filter-repo` + force push | 分支历史里没有了；**但按 SHA 仍可读** |
| 3 | **联系 GitHub Support 请求清除** | 移除悬空对象与缓存视图 ← **只有这步才真正断掉直连访问** |

**结论**：把 force push 当成终点是自欺。要么走完第 3 步，要么如实记录「旧 SHA 仍可读」这个残留风险。

### 改写历史的实操坑

**1. `git filter-repo` 装了 ≠ 能用。** pip 装的版本**不注册成 git 子命令**：

```bash
git filter-repo ...            # ❌ git: 'filter-repo' is not a git command
python3 -m git_filter_repo ... # ✅
```

**2. 交互确认会卡死。** 它跑之前要在终端确认；stdin 不可用（脚本 / agent 里调用）直接 `EOFError` 崩掉。喂确认即可：

```bash
printf 'y\ny\n' | python3 -m git_filter_repo --replace-text <表> --force
```

**3. 回滚快照放 `/tmp` 会丢。** 备份若放会被系统清理的目录，**出问题时将无从回滚**。备份必须放不会被清的目录（如 `~/.backups/<repo>/`），并在 log 里记下路径——否则「可回滚」只是一句空话。

**4. 替换表长串必须排在短串前面。** `--replace-text` 按顺序替换，短串先命中会吃掉长串的前缀，让长串再也匹配不上（互为前缀的词尤其容易中招）。

**5. 改写完验全历史，不能只看 HEAD。** HEAD 干净不代表历史干净：

```bash
for kw in "<敏感串>"; do
  printf "%s → " "$kw"; git log --all -S"$kw" --oneline | wc -l   # 必须为 0
done
```

**6. 技能的多个副本会各自漂移，合并前先判方向。** 主副本（随产品发布的那份）与各宿主的技能副本（例如 `~/.<agent>/skills/`）会分别被改动。两个文件的漂移方向可能正好相反。**先 diff 出谁是超集，再由超集覆盖另一方**，别无脑覆盖——否则会把刚写的教训删掉。判据：`diff` 输出里「仅 A 有 N 行 / 仅 B 有 0 行」→ A 是超集。

## 6. 失败模式速查

| 症状 | 原因 | 修法 |
|---|---|---|
| agent 说「干净」但其实有漏 | 浅检、没列已查类别 | 强制要求声明「已查哪些类别、每类无命中」 |
| 两个 agent 结论高度雷同 | 角度没分开 / 互相可见 | 重派，明确分工与隔离 |
| 同一个问题反复出现 | 只修了症状没修生成规则 | 找到产出该内容的模板/工作流一并改 |
| 审核 agent 顺手把文件改了 | 破坏审改分离 | 回滚它的改动，只采纳报告 |
| 跑了 4 轮还没干净 | 内容本身不适合公开 | **升级给人**，考虑这条内容就不该发 |
| **改了 A 文件，B 文件里同一段文案还留着** | 同一段话被复制到多处（正文 + 模板/工作流注册） | 改完**全文搜这条文案的副本**（漏改副本很常见） |
| **修复后仍出现同类泄露** | 常见原因：写案例/写复盘时把原文抄了回来 | 案例一律**只写模式不写值**；做不到抽象化就不写这个案例 |

## 7. 接入点（这道门要挂在哪）

**判据：凡是内容离开你控制范围的出口，都要过这道门。**

| 出口 | 挂在哪 | 备注 |
|---|---|---|
| **仓库发布** | `tools/publish_os.py`（同步脚本内，落盘前） | 机械扫描命中即中止，脚本退出码非 0 |
| **知乎 / 小红书 / 公众号 / 微博** | 对应生成技能的 **SKILL.md 里写强制指针** | 生成 ≠ 发布；**发布前**必须过门 |
| **对外交付物**（给客户的文档/资料） | 交付清单里的固定一步 | 客户隐私同样不能带出去 |
| **任何公开仓库的 push** | 提交前 | 凡是「随手加一行示例」的位置都要过门 |

**机制说明（重要）**：靠"记得去跑"是不成立的。

- 生成类技能里必须写**强制指针**（「本技能产出在发布前必须过 `release-scrub-gate`」），因为只有 SKILL.md 的 name+description 常驻上下文——**指针写在心里等于没写**；
- 脚本类出口（publish 脚本）把扫描做成**硬闸**：命中即 `exit 1`，不给人"这次算了"的机会；
- 平台发布类没有脚本闸门 → 只能靠指针对齐，所以**指针必须显式写着「发布前」**，不能只写「注意脱敏」。

**最容易漏的三个位置**：

1. **示例行**——为了讲清格式而举的例子（示例里常常自然带出真实的人名、站点名、文件名）
2. **案例复盘**——为了说明"这次泄露了什么"而把原文抄回来（**写防泄露文档时容易犯**）
