# Release Scrub Gate — 发布脱敏三重门

> **「文档自称已脱敏」不能当证据。** 本技能存在的理由来自一次真实事故：
> 一份自称「已脱敏」的公开文档里，**真实私密文件名就躺在示例行里**，公开挂了两个月才被发现。

## 0. 为什么要有这道门

| 你以为的 | 实际的 |
|---|---|
| 我写的文件我自己检查过 | **作者盲区**：自己写的东西自己看不见问题 |
| 机械扫描过了就安全 | 只能抓**确定性**模式（密钥/IP），抓不到**语义泄露** |
| 一个 agent 审一遍就够 | 角度单一 + 互相锚定；**两个独立 agent 才有覆盖** |
| 改掉再推就干净了 | **git 历史永远留着**——改文件 ≠ 删历史 |

## 1. 三重门（顺序不可颠倒）

| 层 | 谁做 | 权威范围 | 性质 |
|---|---|---|---|
| **L1 机械** | grep 正则 / 仓库自带敏感词扫描 | 凭据、密钥、token、IP、账号名、主机名 | **确定性**，命中即中止 |
| **L2 语义** | **2 个独立子 agent**（角度错开） | 语义泄露、反推风险、示例措辞、内部结构残留 | **概率**，必须证据式 |
| **L3 责任** | **人** | 最终签收 | agent 不担责，人担责 |

**L1 先于 L2**：机械扫描是确定性的，几秒钟就能排掉一大类；别让 agent 去找密钥（它会漏）。

## 2. 迭代循环（核心机制）

```
第 1 轮：L1 机械扫描 → 2 个 agent 并行审 → 汇总 findings
         ↓ 有发现
        修（由主 agent 修，审核 agent 不许动文件）
         ↓
第 2 轮：换 2 个【全新】agent 复审（不复用上一轮的，它们会锚定自己上次的结论）
         ↓ 仍有发现
        修 → 第 3 轮
         ↓ 连续一轮【零发现】
        ✅ 脱敏结束 → L3 人工签收
```

**收敛判据（必须同时满足才算一轮 clean）**：

1. 两个 agent 的 `findings` 都是**空数组**；
2. 两个 agent 都在 `verdict` 里**明确声明已查哪些类别、每类无命中**；
3. 主 agent 自己也复跑一遍 L1 机械扫描确认 0 命中。

**成本闸门**：一轮通过才算结束；**最多 5 轮**。若连续轮次都栽在**同一类**问题上，说明问题不在内容而在**你的写法**——停下来改写法，别再派 agent（本次实测：连续三轮都是同一类错误，见 §4 的自检三步）。

> 第 3 轮之后仍在同一位置反复出错时，**不要硬撑轮次**：那说明缺的是一条机械自检规则，不是缺一轮审核。

## 3. 硬纪律（违反即失效）

1. **审与改分离。** 审核 agent **只报告、不修改**。它一改，就失去独立复核（它会把自己改的算作"已清理"）。
2. **证据式 findings。** 每条必须含 `file` / `line` / **`quoted`（原文引用）** / `severity` / `why` / `fix`。**没有原文引用的 finding 不算数；没有引用的「干净」也不算数。**
3. **两个 agent 互相不可见。** 并行派发、各自独立，不要让第二个看到第一个的结论。
4. **角度必须错开**，不是两遍同样的检查：
   - **A：凭据与身份可追溯性** —— 凭据 / 主机网络 / 真人姓名与内部系统 / 私有路径结构
   - **B：业务内幕与个人隐私** —— 业务数字与内幕 / 员工隐私 / 个人财务家庭关系 / 内部决策与上级原话 / **示例措辞** / **组合反推风险**
5. **复审要看 diff 也要看全文。** 修复本身可能引入新泄露（例如把一个真实名字换成另一个真实名字）。
6. **每轮换新 agent。** 复用会锚定上次结论，还会把"上次没报"当成"没问题"。

## 4. 这类泄露长什么样（机械扫描全漏）

> **⚠️ 本节及任何公开文档只写「模式」，绝不写具体值。**
> 讲案例时把真实地名 / 人名 / 文件名 / 原句抄进公开文档 = **二次泄露**。
> 本次实测就发生过：第一轮从正文删掉了真实站点名，第二轮新写的「案例复盘」里又把它抄了回来。

| 泄露模式 | 为什么机械扫描抓不到 |
|---|---|
| 人称暗示「这是为某个特定的人做的」 | **反推线索**：读者能推断出给谁做的 → 熟人可对号入座 |
| 示例行里自然带出真实私密文件名 | 它是「示例格式」的产物，正则扫不到 |
| 示例里出现真实市场 / 站点 / 店铺名 | 看起来只是随手举的例子 |
| 对真实关系人（上级 / 同事 / 客户）的性格或评价 | **语义级泄露**：复述了真实关系与判断 |
| 复述事件时把原文抄回来 | **写防泄露文档时最常犯**——案例本身变成了新的泄露源 |

**共性：它们都不是「秘密」，但读了就等于知道了私事。** 这类只能靠语义审核发现。

**两条配套硬规则**：

1. **审核 agent 的 finding 必须带原文引用**（否则不可复核）——但那份报告**只进本地对话，绝不进任何公开文件**；
2. **公开文档里讲案例只能写模式、不能写值**——做不到抽象化就干脆不写这个案例。

### 案例自检三步（机械执行，别靠记性）

**这条规则是被现实逼出来的：连续三轮修复，每一轮都栽在同一类错误上——写案例时顺手把具体值抄了回去。**「记住要抽象」没有用，必须机械检查：

1. **抽值**：把案例段落里所有 `「」`、`""`、反引号包着的内容抽出来；
2. **替换测试**：把它们统统换成 `[值]`，如果句子**仍然成立** → 说明这个值不是必需的 → **删掉它**；
3. **回搜**：把删掉的值拿去**全文（及所有副本文件）搜一遍**，确认没有残留在别处。

> 判据：**案例句里出现被引号包起来的专有名词 = 危险信号。** 抽象案例里不需要任何专有名词。

## 5. GitHub 的现实（改文件 ≠ 删历史）

发布后发现泄露，**推一个新 commit 覆盖是不够的**：

- 旧 commit 里的原文**永远可访问**（`github.com/<owner>/<repo>/blob/<旧SHA>/<file>`）
- 搜索引擎可能已索引
- **fork 里的副本无法收回**（先查 `forks_count`！0 fork = 暴露面可控）

**补救顺序**：
1. **先止血**：改内容 + 推新 commit（无论如何都要做）
2. **查暴露面**：`gh api repos/<owner>/<repo> --jq '{forks:.forks_count, stars:.stargazers_count}'`
3. **要不要改历史**：`git filter-repo` / BFG + force push —— **不可逆、会改写所有 SHA**，必须人拍板
4. **事后**：检查搜索引擎缓存；敏感度高时联系 GitHub Support 清理

**判据**：0 fork + 低敏感度 + 受众小 → 可以只做第 1 步并记录决策；有 fork 或高敏感度 → 必须改历史。

## 6. 失败模式速查

| 症状 | 原因 | 修法 |
|---|---|---|
| agent 说「干净」但其实有漏 | 浅检、没列已查类别 | 强制要求声明「已查哪些类别、每类无命中」 |
| 两个 agent 结论高度雷同 | 角度没分开 / 互相可见 | 重派，明确分工与隔离 |
| 同一个问题反复出现 | 只修了症状没修生成规则 | 找到产出该内容的模板/工作流一并改 |
| 审核 agent 顺手把文件改了 | 破坏审改分离 | 回滚它的改动，只采纳报告 |
| 跑了 4 轮还没干净 | 内容本身不适合公开 | **升级给人**，考虑这条内容就不该发 |
| **改了 A 文件，B 文件里同一段文案还留着** | 同一段话被复制到多处（正文 + 模板/工作流注册） | 改完**全文搜这条文案的副本**（本次实测：技能正文里的人称代词被改成中性写法，另一个文件里复制过去的同一段漏改，第 2 轮才被抓到） |
| **修复轮次又引入同类泄露** | 写案例/写复盘时把原文抄了回来 | 案例一律**只写模式不写值**；做不到抽象化就不写这个案例 |

## 7. 接入点（这道门要挂在哪）

**判据：凡是内容离开你控制范围的出口，都要过这道门。**

| 出口 | 挂在哪 | 备注 |
|---|---|---|
| **仓库发布** | `tools/publish_os.py`（同步脚本内，落盘前） | 机械扫描命中即中止，脚本退出码非 0 |
| **知乎 / 小红书 / 公众号 / 微博** | 对应生成技能的 **SKILL.md 里写强制指针** | 生成 ≠ 发布；**发布前**必须过门 |
| **对外交付物**（给客户的文档/资料） | 交付清单里的固定一步 | 客户隐私同样不能带出去 |
| **任何公开仓库的 push** | 提交前 | 尤其是 AGENTS/README 这类「随手加一行示例」的地方——**本次两处泄露都在示例行里** |

**机制说明（重要）**：靠"记得去跑"是不成立的。

- 生成类技能里必须写**强制指针**（「本技能产出在发布前必须过 `release-scrub-gate`」），因为只有 SKILL.md 的 name+description 常驻上下文——**指针写在心里等于没写**；
- 脚本类出口（publish 脚本）把扫描做成**硬闸**：命中即 `exit 1`，不给人"这次算了"的机会；
- 平台发布类没有脚本闸门 → 只能靠指针对齐，所以**指针必须显式写着「发布前」**，不能只写「注意脱敏」。

**最容易漏的三个位置**（实测）：

1. **示例行**——为了讲清格式而举的例子（示例里常常自然带出真实的人名、站点名、文件名）
2. **案例复盘**——为了说明"这次泄露了什么"而把原文抄回来（**写防泄露文档时最常犯**）
3. **旧文件**——别人告诉你"这份已经脱敏过了"，那就更要查（本次两处泄露都在自称已脱敏的文件里）
